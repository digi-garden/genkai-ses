# 依頼2：変更によって生まれた新しい問題の確認
特に次の点を確認してください。
1. 山札の仕組みの組み合わせ：未読カードの優先、初回の序盤カードの優先、スタイル別カード、連鎖カードの注入、山札切れ時の再シャッフル。これらを同時に適用したとき、挙動が矛盾したり、一意に決まらなかったりしないか。
2. シミュレータの合格基準（7.5）：
   - 基準同士が同時に満たせるか（例：random の生存週の中央値が Week 8〜15 であることと、greedy のクリア率 15〜35% の両立）。
   - Bot の定義は、実際のプレイヤーの代わりとして妥当か。
   - 死因の優先順位（資金＞コンプラ＞現場＞顧客）がある中で、「各死因 5〜25%」の基準は現実的か。
3. 切り札の操作（予兆ドット＋毎回2段階）：テンポの要件（トランジション0.3秒以下）や、キーボード・スワイプ・ボタン操作との競合がないか。誤操作で取り消してしまう／発動してしまう、という問題が起きないか。
4. 連鎖による「敗因」表示：「連鎖カードの解決で死亡した場合のみ」という定義は妥当か。連鎖カードの数ターン後に、その影響で死んだ場合の扱いをどうすべきか。
5. 導入カード（初回の Week 1〜2）：週を消費することで、生存カーブ・売上式・称号判定（Week 14 以降）・KPI（Week 13 到達）に影響が出ないか。
6. 暫定値の妥当性：スタイルのパッシブと切り札の新しい値（特に技術至上主義の切り札の cash -25）や、称号の閾値（コンプラ65以上・資金40以下）が、新たな支配戦略や「使えない切り札」を生まないか。
7. 型定義と本文の整合：TypeScript の型（Choice、EventCard、PendingInjection、RuntimeGameState、SaveData）と本文の仕様に、食い違いや不足がないか。v1.8 以前のルールが本文に残っていないか。
8. 工数：77枚のカード執筆とシミュレータの作成を加えて、総工数40〜60時間に収まるか。収まらない場合、何を削るべきか。
