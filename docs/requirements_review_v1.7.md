# 要件定義書 v1.7 レビュー結果（v1.8 改訂に向けて）

> 作成日：2026-10-31 ／ 対象：`docs/requirements.md`（確定版 v1.7）
> 目的：基本設計に入る前に、矛盾・実装不能箇所・未定義事項を洗い出し、改訂方針を決める。
> 区分：**【A】重大**＝仕様どおり実装すると破綻する ／ **【B】要決定**＝オーナー判断が必要 ／ **【C】補完**＝推奨案で埋めればよい

## 【A】重大（そのままでは成立しない）

### A-1. 称号『ホワイト企業の鑑』『自転車操業マスター』が取得不可能
- コンプラ初期値は50なので、ラン開始時点で `minLegalDuringRun = 50` となり、`>= 80` は**絶対に満たせない**。
- 資金初期値も50なので、`maxCashDuringRun <= 30` も**絶対に満たせない**。
- **改訂案：** 判定の対象期間を「Week 14（第2四半期）以降」に限定する。
  - `minLegalSinceQ2 >= 80`、`maxCashSinceQ2 <= 30` として記録する（Week 13 の決断が終わった時点から計測）。

### A-2. 称号『人月搾取の帝王』がクリアするたびに自動で取れてしまう
- 売上式は `生存週数×200 + cash×10`（単位は万円）。クリア時には `52×200 = 10,400万` となり、資金がいくらでも**1億円を必ず超える**。
- 3.1-5 の本文「ターン経過および選択肢の cash 増加分を累積」と計算式も一致していない。
- **改訂案（推奨）：** 本文どおり、増加分を累積する式に変える。
  - `totalSales = 生存週数×100 + Σ(選択で増えた cash の正の値)×50`
  - クリアで最低5,200万、帝王（1億）を取るには cash 増加の累計が約96必要になる。
  - 係数はバランス調整で最終決定する。

### A-3. 初見の生存カーブと「有効プレイ成立率」の KPI が衝突している
- 初見プレイの平均生存を Week 8〜15 で設計すると、約半数が Week 13 に届かない。
- 有効プレイの定義は「Week 13 到達」なので、**初回だけで 60% を達成するのは構造的に難しい**。
- **改訂案（どちらかに決める）：**
  - ① 有効プレイの定義を「Week 8 到達」に下げる。
  - ② 定義はそのままで、「ユーザー単位で、いずれかのプレイで Week 13 に到達」と読み替える（リプレイを前提にする）。**← 推奨**

### A-4. 切り札の発動で即死するケースが未定義
- 体育会系の『精神論チャージ』（dev +40）は、dev が60以上の状態で使うと100に達して「技術オタク化」で死ぬ。
- 技術至上主義の『全パラメータ +15』も、85以上の項目があれば即死する。
- **改訂案：** 次の2つから決める。
  - 「切り札の効果も通常の判定対象（即死あり）」として、プレビューで警告する。
  - 「切り札の効果は 1〜99 にクランプする（切り札では死なない）」とする。**← 推奨**（救済スキルとしての体験を優先）

## 【B】要決定（ゲーム体験・運用方針）

| # | 論点 | 推奨案 |
|---|---|---|
| B-1 | パッシブ倍率の方向。「現場メンタル減少×0.8」と 3.1-6「増減どちらにも符号のまま乗算」が矛盾して読める | 倍率は**名前どおりの方向だけ**に掛ける（減少×0.8は減るときだけ、獲得資金×1.3は増えるときだけ）。3.1-6 の文言は「符号は変えない」という意味に修正する |
| B-2 | 切り札の効果にパッシブ倍率を掛けるか | 掛けない（固定値） |
| B-3 | 2〜3回目で「Week 26 の壁」に当てる難易度カーブを、ランダム山札でどう実現するか | `play_count` を見る。初回は「即死しやすい序盤カード群」を優先して引かせ、2回目以降は通常の抽選にする。適応的な難易度調整はしない |
| B-4 | ゲージに数値を見せるか | 見せない（Reigns 同様に量だけを示す）。予兆ドットは、変化量が大きいか小さいかで大小2段階にする |
| B-5 | AdSense の「プレイ画面最下部バナー」 | スワイプ・ボタンの直下なので**誤クリックを誘う配置としてポリシー違反のリスク**がある。タイトル画面とリザルト画面だけに移す。また、ゲーム中心の SPA は「有用なコンテンツ不足」で審査に落ちやすいので、遊び方や図鑑の説明文などテキストページを用意する |
| B-6 | 計測ツール | Cloudflare Web Analytics はカスタムイベントを送れない。イベント計測は **GA4**、UU とパフォーマンスは CF Web Analytics と役割を分ける |
| B-7 | 季節固定イベントが各週1枚だけだと、毎回同じでリプレイが単調になる | 固定週ごとに2〜3枚の候補を持ち、そこから抽選する（MVP は各1枚、Phase 2 で増やす） |

## 【C】補完（推奨案で仕様化する）

### ゲーム進行ルールの明確化
- **C-1 ターン処理順：** 次の順に固定する。
  1. カード表示
  2. 選択
  3. 倍率を掛ける
  4. 丸める
  5. 加算してクランプ
  6. 極値（最小・最大）を記録
  7. 連鎖注入を予約
  8. **死亡判定**
  9. 週を +1
  10. 週が52を超えていればクリア
- **C-2 死亡週の定義：** 「第N週に倒産」は、死亡したカードの週番号Nとする。生存週数は N−1、クリア時は52。
- **C-3 Week 52 の扱い：** Week 52 のカードで崩壊した場合は**死亡を優先**する（クリア扱いにしない）。
- **C-4 丸め：** `Math.round(-2.5) = -2` となり、負の値で非対称になる。符号付き四捨五入（0から遠い方へ）に統一する。
- **C-5 連鎖注入の衝突：**
  - 注入予定の週が固定イベントの週と重なったら、翌週にずらす。
  - 同じ週に複数の注入があれば、予約した順に1週ずつ後ろへずらす。
  - Week 52 を超えた注入は破棄する。
- **C-6 注入する週の指定方法：** 絶対週ではなく相対週にする。`Choice` に `inject_delay: [min, max]` を追加する（例：`[3, 10]`）。
- **C-7 切り札の操作：** ターンを消費せず、現在のカードを表示したまま即時に適用する。適用直後の死亡判定はしない（A-4 の推奨案に従う）。固定イベントの週でも使える。

### データ構造の不足
- **C-8 `RuntimeGameState` / `SessionSnapshot` に追加する項目：**
  - `styleId`
  - `companyName`
  - `currentCardId`（リロード時に同じカードを出すため）
  - `deck`
  - `usedCardIds`
  - `cashGainedTotal`
  - `runStartedAt`
  - `minLegalSinceQ2` / `maxCashSinceQ2`
- **C-9 ID 体系の統一：** 結末IDは `cash_zero` / `cash_max` / `client_zero` / `client_max` / `dev_zero` / `dev_max` / `legal_zero` / `legal_max` / `clear` の9種。
  - 画像：`end_{id}.webp`
  - URL：`/results/{id をケバブケースにしたもの}`（例：`dev-zero`）
  - 計測：`reason_id = id`
- **C-10 Store-Safe Mode の範囲：** カードのテキストだけでなく、**経営スタイル名・切り札名・結末名・称号名・話者名**にも web / store の両表記が必要。UI 文言辞書（`strings.ts`）で一元管理する。
- **C-11 `SaveData` に追加する項目：** `last_company_name`（入力の手間を減らすため）。マイグレーション方針も決める（`schema_version` が不一致なら変換関数を通し、失敗したら初期化）。
- **C-12 称号が同時に複数取れた場合：** すべて図鑑に登録する。シェア文と `achievement_id` には、優先度（レア度）が最も高い1つだけを載せる。

### 画面・非機能
- **C-13 画面遷移を定義する：**
  - タイトル → 会社名入力 → 経営スタイル選択 → プレイ → リザルト → （リトライ / タイトル）
  - タイトルから図鑑、遊び方、規約の各モーダルを開ける。
  - `/results/:id` は OGP 用の静的ページ。人がアクセスしたら「その結末の紹介と、プレイするボタン」を表示する。
- **C-14 OGP の実現方式：** X のクローラーは JS を実行しないので、**ビルド時に9種の静的 HTML を生成**する。Cloudflare Pages の SPA フォールバックと静的ファイルの優先順位は基本設計で検証する（`_redirects` が本当に必要かどうかも含む）。
- **C-15 シェア URL：** 流入を計測するため `?utm_source=x&utm_medium=share` を付ける（K-factor の算出に使う）。
- **C-16 対応環境：**
  - iOS Safari 16 以降
  - Android Chrome 最新版
  - PC：Chrome / Edge / Firefox / Safari の最新版
- **C-17 アクセシビリティ：** `prefers-reduced-motion` 対応。ゲージは色だけでなくアイコンと量でも判別できるようにする。
- **C-18 サウンド：** 初期状態は OFF。AudioContext はユーザー操作の後で生成・再開する（モバイルの自動再生制限への対策）。
- **C-19 法務：**
  - GA4 と AdSense の外部送信について、プライバシーポリシーに記載する（改正電気通信事業法の外部送信規律）。
  - EEA / 英国からのアクセスには、AdSense が Google 認定の同意管理（CMP）を求める。対象地域では広告を出さないか、CMP を導入する。
- **C-20 離脱の計測：** `drop_at_week_X` は `visibilitychange`（hidden）で `navigator.sendBeacon` を使って送る。
- **C-21 KPI 算出に必要なパラメータ：** すべてのイベントに `play_count` と `days_since_first_play` を付ける（D1 / D7 の算出用）。
- **C-22 開発体制の記述：** 「AIエージェント Antigravity による実装」を実際の体制に合わせて更新する。
