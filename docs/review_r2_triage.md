## 詳細

### 指摘1：カードプール → 修正して採用
- 問題の認識は正しい。前回の観点リストでも同じ点を挙げていた。
- ただし**改善案A（条件付きカードで、総枚数を増やさずに体感のプールを広げる）は、単独では効果がない**。
  - 1ランに必要なドロー数（最大48）は変わらない。50枚の中にスタイル別カードを含めると、1ランで引ける候補が約40枚に減ってしまい、かえって山札切れと再シャッフルが早まる。
- 実態として、序盤〜中盤で倒産するランが多いため、1ランで引くのは平均10〜25枚。問題が深刻になるのは、3〜6回目以降に Week 26〜52 まで進めるようになってからである。
- **採用案：**
  1. **未読カードを優先する**：これまでに見たカードIDを `SaveData.seen_card_ids` に記録し、山札を作るときに未読カードを前の方に寄せる。実装コストが小さく、最も効果が大きい。
  2. **スタイル別カードを追加枠にする**：各スタイル5枚（計15枚）を、通常50枚とは別に足す（1ランの候補は55枚）。
  3. **ピンチカード**（いずれかのパラメータが危険域のときだけ混ざる）は Phase 2 に回す。山札の挙動が複雑になり、シミュレータでの検証範囲も広がるため。
  4. 改善案B（MVPのゴールを26週に短縮）は**不採用**。世界観、季節イベント、KPIへの影響が大きすぎる。
- MVPのカード総数をどうするかは、オーナーの判断が必要（執筆量が変わるため）。

### 指摘2：シミュレータ → 採用（最優先）
- ゲームロジックは純粋関数として分離する方針なので、低コストで作れる。乱数のシード固定（観点7）も同時に導入する。
- **Bot の戦略（3種）：**
  - `random`：完全にランダムに選ぶ。初見プレイヤーの代わり。
  - `greedy`：選んだ後、4つのパラメータが50から最も離れない方を選ぶ。上級者の代わり。
  - `gambler`：`cash` が増える方を優先する。
- **合格基準（初期値。Week 4 に見直す）：**
  - `random` の生存週数の中央値が Week 8〜15 に収まる。
  - `greedy` のクリア率が 15〜35% に収まる。
  - 8種の死因の発生比率が、どれも5%以上・25%以下に収まる（`random` と `greedy` の合算）。
  - スタイル別の `greedy` クリア率の差が、10ポイント以内に収まる（指摘6）。
  - 各称号の `greedy` での取得率が、クリアしたランのうち 1% 以上に収まる（指摘5）。
- カードの JSON 検証（スキーマ、`inject_card_id` の参照先、効果値の範囲）も同じスクリプトで行う。

### 指摘3：切り札の警告 → 要再決定
- 指摘には一理ある。⚠表示は「死ぬかどうか」という確定情報を与えてしまい、ゲージの数値を隠した方針と整合しない。
- 一方で、切り札の効果値は固定なので、ゲージの量を見ればある程度は予測できる。警告がなくても完全な運任せにはならない。
- **選択肢：**
  - (a) 現行どおり。即死するときだけ⚠を表示し、2段階操作にする。
  - (b) **予兆ドットに統一する**。ボタンにホバーまたは長押しすると、通常カードと同じ予兆ドットがゲージに点滅する。確認の2段階操作は**毎回**行い、即死するかどうかは明かさない。**← 推奨**
  - (c) 確認の演出だけにする（予兆ドットも出さない）。

### 指摘4：連鎖の因果関係 → 採用（拡張）
- 案A（`kind: 'chain'` のカードに「【因果応報】」バッジを付け、短い演出を入れる）と、案B（連鎖カードの本文の書き出しで、過去の選択に言及することを執筆ルールにする）の**両方を採用**する。
- **拡張：** 連鎖カードが原因で死亡した場合、リザルトに「敗因：第5週『新人の経歴をJava歴3年に盛った』」と表示する。
  - これは 3.4 のシェア文の例「新人の経歴を盛ったのがすべての間違いでした」をデータで実現する仕組みでもある。
  - `PendingInjection` に `originWeek` と `originChoiceText` を持たせ、`Choice` に `regret_text?`（敗因として表示する一文）を追加する。

### 指摘5：称号の取得難度 → 修正して採用
- 指摘の「天文学的に低い確率」は言い過ぎ。ランダムに選ぶ場合の話であり、予兆ドットを見て意図的に操作すれば狙える。
- ただし、数値を表示しない状態で20〜30ポイントの幅に39ターン留まり続けるのは、確かに厳しい。
- **採用案：** 暫定の閾値を `maxCashSinceQ2 <= 40`、`minLegalSinceQ2 >= 65` に緩める。最終値は、シミュレータでの取得率の基準（指摘2）で決める。条件そのものの作り替え（改善案A）は不採用。単純な条件の方が、プレイヤーにとって狙いを理解しやすいため。

### 指摘6：スタイル間の性能差 → 修正して採用
- 方向性は妥当。補足すると、v1.8 では切り札でも即死するため、技術至上主義の「全パラメータ +15」は、85以上の項目があると死ぬ。純粋な防御手段ではない。
- **採用案：** 提示された数値は初期値の候補として扱い、スタイル別クリア率の差が10ポイント以内（指摘2）に収まるようにシミュレータで調整する。
  - 技術至上主義の切り札：`dev +30 / client +20 / cash -25`（候補）
  - グレー派遣ブローカー：切り札を `legal -25` にし、パッシブを `コンプラ減少 ×1.3` にする（候補）
- 『人月搾取の帝王』の閾値は、スタイル別の取得率を見て決める。

### 指摘7：チュートリアル → 採用
- 初回プレイ（`play_count == 0`）の Week 1〜2 に、導入カード（`kind: 'tutorial'`。話者は秘書）を置く。効果は小さくし、選択肢はどちらを選んでも数値が少し動く程度にする。
  - Week 1：操作方法（スワイプ、キー、ボタン）
  - Week 2：「0でも100でも倒産」「予兆ドット」
- **リザルト画面**に、どのゲージがどちら向きに振り切れたかを図で示す（「現場メンタルが**100に達して**倒産」）。
- 2回目以降は、導入カードを表示しない（遊び方のモーダルからいつでも読める）。

### 指摘8：シェアの導線 → 採用
- **モバイル（Web Share APIでファイルを共有できる環境）：** 画像を添付してシェアする導線をメインにする。
- **PC：** ［Xでポスト］ボタン（OGPカードが表示される）の横に、［画像をコピー］［画像を保存］ボタンを置き、「画像を貼るともっと自慢できます」という一文を添える。クリップボードに画像を書き込めないブラウザでは、［画像を保存］だけを表示する。
