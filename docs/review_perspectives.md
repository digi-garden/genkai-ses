# 要件定義書 v1.8 追加レビュー観点

> 目的：`requirements_v1.8.md` を別のAIにレビューさせるための観点リスト。
> 前回のレビュー（`requirements_review_v1.7.md`）は**仕様の論理的な矛盾と実装できない箇所**が中心だった。今回はそれ以外の観点で見てもらう。
> 各観点の「確認ポイント」は、レビュー担当の着眼点の例として渡す（網羅を求めるものではない）。

---

## 1. ゲームデザイン（面白さ・リプレイ性）
- コアループ（2択→パラメータ変動→崩壊回避）が、52週の間ずっと緊張感を保てるか。
- どちらを選んでも同じになる選択や、常に正解が決まっている選択（支配戦略）が生まれない設計になっているか。
- **カードの消費量**：1ランで通常カードを約48枚引くのに、MVP の通常カードは50枚しかない。ほぼ毎回すべてのカードを見ることになり、2回目以降の新鮮さが保てるか。
- 経営スタイル3種に本当に差が出るか。最強のスタイルが1つに決まってしまわないか。
- 切り札（即死あり）、連鎖イベント、季節イベントが、意味のある判断を生むか。
- Reigns など先行作との違いが、風刺の題材以外にもあるか。

## 2. 難易度・数値バランス
- 初見で Week 8〜15 に撃沈、4〜6回目で完走という生存カーブを、カード効果量（±いくつ）で実際に作れるか。モンテカルロ・シミュレーションでの検証方針があるか。
- 8種の死因が偏りなく発生するか（死因の優先順位による偏りへの対策は十分か）。
- パッシブ倍率によって、特定の称号（例：グレー派遣ブローカーと『人月搾取の帝王』）が極端に取りやすくならないか。
- 売上式の係数、称号の閾値、注入遅延 `[2, 6]` などの初期値は妥当か。

## 3. 風刺表現・炎上リスク
- SES業界の描写として「あるある」の解像度が十分か（当事者が読んで共感できるか、ずれていないか）。
- 風刺の矛先が、構造（多重下請け・人月商売）に向いているか。弱い立場の個人（新人・下請け・退職者）を笑いものにする方向になっていないか。
- 偽装請負・経歴詐称などの違法行為を、肯定や推奨と受け取られる表現になっていないか。
- 実在の企業・サービスを想起させるリスク、差別的・ハラスメント的な表現の有無。
- SNSで拡散されたときに、業界団体・企業・当事者から批判を受けたり炎上したりするシナリオと、その対策。
- 12+ のレーティング想定が妥当か。

## 4. 法務・規約・ポリシー
- AdSense のプログラムポリシー（コンテンツの有用性、広告の配置、誤クリック）を満たせるか。
- Apple App Store Review Guidelines（1.1 不快なコンテンツ、4.2 最低限の機能、Web をラップしただけのアプリとして却下されるリスク）と Google Play のポリシー。
- 生成AIで作った画像の権利関係と、各サービスの利用規約上の商用利用の可否。
- プライバシーポリシー、外部送信規律、EEA 向けの同意管理（CMP）、Cookie の扱い。
- 将来の課金に必要な対応（特定商取引法に基づく表記など）。

## 5. バイラル・マーケティング
- シェア定型文、OGP画像、挑戦状形式のフックが、実際に「シェアしたくなる」ものになっているか。
- K ≧ 0.2 の前提（シェア率5%、1投稿あたりの流入4人）は現実的か。
- 初期流入施策（Qiita / Zenn の開発記事、X のエンジニアクラスタ）の具体性と、公開1ヶ月で 10,000 UU という目標の妥当性。
- X の Web Intent や OGP カード表示の仕様が変わるリスクと、代替のシェア手段。

## 6. KPI・計測設計
- 各 KPI が、定義どおりに計測できるイベント設計になっているか（分母と分子が取れるか）。
- **エンジニア層は広告ブロッカーの利用率が高く**、GA4 の数値が大幅に過少になるおそれがある。Go/No-Go の判定にどう影響するか、補正の方法はあるか。
- 同意管理（CMP）による計測の欠損。
- LocalStorage に頼ったリテンション計測の限界（ブラウザの変更、シークレットモード、ITP による削除）。
- Go/No-Go の閾値そのものが、アプリ化の判断基準として妥当か。

## 7. 技術・アーキテクチャ
- 技術スタック（React + Vite + Tailwind + framer-motion + html-to-image）の選定は妥当か。もっと軽くできる代替はあるか。
- ゲームロジックを純粋関数として分離する設計と、テストのしやすさ。**乱数のシード固定**（テストの再現やバグ報告のため）が必要ではないか。
- 将来 Capacitor や React Native へ移植するときの障害（`SaveRepository` 以外の Web 依存：Web Share、html-to-image、Web Audio）。
- html-to-image の iOS Safari での制約に対する代替案（Canvas に直接描く、あらかじめ用意した画像に文字だけ重ねる、など）。
- カードデータ（JSON）の検証方法：スキーマ検証、存在しない `inject_card_id`、効果値の範囲チェックを CI で行うか。

## 8. UX・UI・アクセシビリティ
- モバイルで、スワイプとブラウザの「戻る」ジェスチャーやページのスクロールがぶつからないか。片手で操作できるか。
- **等幅フォント指定（JetBrains Mono など）には日本語の字形がない**。日本語部分のフォールバックと、読みやすさ。
- カード本文の文字数の上限（小さい画面で読み切れる量か）。
- 初見ユーザーが、説明なしで操作方法（スワイプ・ボタン・切り札）を理解できるか。チュートリアルは必要か。
- 色覚の多様性への配慮、`prefers-reduced-motion`、スクリーンリーダーへの最低限の対応。

## 9. パフォーマンス・運用
- 初回表示の目標値（LCP や JS バンドルサイズ）が定義されているか。17枚の一括プリロードは、モバイル回線で重すぎないか。
- Cloudflare Pages の無料枠、キャッシュ戦略、デプロイ手順。
- 公開後の運用：カードの追加・修正の手順、不具合の報告窓口、問い合わせ対応。

## 10. スケジュール・工数・スコープ
- 週4〜8時間 × 8週間（40〜60時間）で、カード100枚の執筆、アセット17枚、OGP、広告、計測、法務ページまで収まるか。
- 遅れたときに削る機能の優先順位（MVP の最小構成）が明確か。
- カードのテキスト執筆とバランス調整という、見積もりから漏れがちな工数が考慮されているか。

## 11. 事業性・マネタイズ
- Web 版での AdSense 収益の見込み（ほぼゼロ前提で問題ないか）と、PoC 判定との関係。
- アプリ化したときの損益分岐（リワード広告で月間 DAU 1,000〜2,000）の前提は妥当か。
- 買い切りの価格帯と、隠し経営スタイルを解放する施策の魅力。

## 依頼文の雛形（別のAIに渡す用）

```
あなたはゲーム企画・Webサービス開発の経験が豊富なレビュアーです。
添付の要件定義書（requirements_v1.8.md）をレビューしてください。

# 前提
- 個人開発のWebゲーム（Reigns型の業界風刺シミュレーション）。開発期間は8週間、総工数40〜60時間。
- 仕様の論理的な矛盾・実装できない箇所は、既にレビュー済み（requirements_review_v1.7.md）。そこで決定済みの事項を蒸し返す必要はない。

# 観点
review_perspectives.md の観点 [ここに番号を記入。例：1, 2, 3, 6] を中心に見てください。
観点リストにない問題に気づいた場合も挙げてください。

# 出力形式
指摘ごとに、次の項目を書いてください。
- 重要度：高（リリースや目的達成を妨げる）／中（品質や成果に大きく影響する）／低（改善提案）
- 該当箇所（要件書の章番号）
- 問題点（何が・なぜ問題か）
- 改善案（具体的に。複数案ある場合は推奨案を明示）
最後に、全体の所感と、最優先で直すべき上位3件を挙げてください。
```

### 使い方のヒント
- 観点を1回で全部渡すより、**2〜4観点ずつに分けて**依頼した方が、指摘が深くなる。
  - 例：「1・2（ゲーム性）」「3・4（表現と法務）」「5・6・11（グロースと事業）」「7・8・9・10（開発と運用）」
- 観点3（風刺表現・炎上）は、カード本文がまだないので、カードの執筆後にもう一度レビューするのが効果的。
- 返ってきた指摘は、このリポジトリで「採否と理由」を整理し、v1.9 に反映する。
