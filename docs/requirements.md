> **v1.7 更新概要：** iOS（App Store）およびAndroid（Google Play）のストア審査対策・法務ポリシー要件を追加。違法行為・公的機関名称のマイルド版エイリアス/言い換え指針、ストア審査用テキスト切り替え（Store-Safe Mode）スキーマ設計、フィクション免責事項の常設、対象年齢レーティング（12+）の事前規定。

## 1. プロジェクト概要

* **正式名称：** **限界SES社長 〜人月ピラミッドの頂点へ〜**
* **アプリ内略称（UI表示用）：** **限界SES社長**
* **英題 / リポジトリ名：** `genkai-ses`
* **ジャンル：** Reigns型 業界風刺テキストシミュレーションゲーム（ローグライク要素あり）
* **プラットフォーム：** Webブラウザ（PC / スマホ両対応・レスポンシブ） ＋ 将来のネイティブアプリ展開（iOS / Android）
* **キャッチコピー / サブタイトル（Web版・ストア版エイリアス）：**
  * **Web版キャッチコピー：**
    > **「今期も、誰もバックれませんように。」**
    > *偽装請負、スキル詐称、炎上案件……2択で生き残るSES経営シミュレーター*
  * **ストア掲載用サブタイトル（審査NG回避用マイルド版）：**
    > **「デスマーチ、炎上案件、理不尽な無茶振り……2択で生き残るIT経営シミュレーター」**
* **ターゲット層：** 20〜30代のITエンジニア、SES・SIer・受託開発従事者
* **対象年齢レーティング（ストア申請用）：** **12歳以上（12+ / 中学生以上対象）**（※風刺・不快なユーモア・ブラック企業描写を含むため）
* **フィクション免責事項（タイトル画面下部・規約モーダル常設）：**
  > 「本作はフィクションであり、実在の人物・企業・団体・事件とは一切関係ありません。また、作中に登場する法令違反・不当な労働行為を推奨・助長する意図は一切ございません。」
* **コア体験：**
  * 業界「あるある」の無理難題に対し、スワイプ・キーボード・ボタン双方で2択の決断を下し続ける。
  * **「悪魔の決断」が後々大炎上を生む因果応報（ミニ連鎖イベント）** と、季節ごとの危機（デスマーチ・決算）を乗り切る緊張感。
  * 4大パラメータの崩壊（0または100）を回避しながら、1年間（52週＝52ターン）会社を存続させる。
  * 獲得した「称号（アチーブメント）」や自虐に満ちた「死に様（倒産報告書）」をX等のSNSにシェアして共感を得る。

### 1.1 Web版PoC判定基準（アプリ化ゲート条件 / Go-No-Go KPI）
Web版リリース後2〜4週間の実績データを基に、スマホアプリ化（iOS/Androidネイティブ開発）への追加投資を行うか否かを判断する厳格な定量的基準：

1. **初期流通・シード獲得：** 公開1ヶ月で **10,000 UU 以上**（Qiita/Zenn開発秘話、Tech系コミュニティ、X特定クラスタへの投下によるオーガニック獲得）。
2. **有効プレイ成立率：** **60% 以上**（開始10秒での即時離脱を除外した「第13週（春イベント）以上に到達した上でゲームオーバーまたは完走したユーザー」の割合）。
3. **即時リプレイ性：** 1人あたり平均プレイ回数 **2.5回 以上**（初回死亡後の「もう1回！」ループの成立）。
4. **継続率（リテンション）：** **D1リテンション 15% 以上** / **D7リテンション 5% 以上**（LocalStorage/Cookieによる再訪トラッキング）。
5. **バイラル係数（K-factor）：** **K ≧ 0.2**（リザルト到達者のSNSシェア率 5% 以上 ＋ シェア1投稿あたりの平均流入4人以上）。

## 2. 開発・技術前提条件

* **開発リソース：** 週4〜8時間 × 8週間（総稼働：約40〜60時間）
* **開発体制：** 個人開発（AIエージェント「Antigravity」による実装）
* **技術スタック：**
  * **フロントエンド：** React (v18+) + TypeScript + Vite
  * **スタイリング：** Tailwind CSS + Lucide React（アイコン）
  * **カードUI / アニメーション：** `framer-motion`（スワイプ・ドラッグ・フリック対応）
  * **ホスティング：** **Cloudflare Pages**
  * **データ永続化：** **LocalStorage のみ**（外部DB・サーバー構築は一切行わない）
  * **画像生成：** **`html-to-image`** によるクライアントサイドPNG生成
  * **アセット調達：** 生成AIによるドット絵静止画（計17枚・WebP形式）
* **アーキテクチャ方針（将来のアプリ化移植を見据えて）：**
  * ゲームロジック（カード効果計算・パラメータ管理・ゲームオーバー判定・称号判定）は、UI（React コンポーネント）およびストレージ実装（LocalStorage / sessionStorage）から分離した純粋な関数群・モジュールとして実装する。
  * ストレージアクセスは直接 `localStorage.getItem/setItem` を呼ばず、`SaveRepository` インターフェース越しに行う（将来 React Native / Capacitor 移植時に AsyncStorage 等へ差し替え可能にするため）。

## 3. 機能要件（Functional Requirements）

### 3.1 ゲームコアロジック

1. **4大パラメータ管理：**
   * 各パラメータは `0〜100` の整数値で管理（初期値は各50）。
   * 変動時は `0 <= value <= 100` にクランプ（Clamp）処理を行う。
   * いずれかが「0」または「100」に達したターン終了時に**即ゲームオーバー**。
   * 全52ターン（1年間）生存で「1期完走（ゲームクリア）」。

| パラメータ名 | 英語表記 | 初期値 | 0になった時（下限死） | 100になった時（上限死） |
| :--- | :--- | :--- | :--- | :--- |
| **資金** | `cash` | 50 | **黒字倒産**（入金ズレで資金ショート） | **買収・内紛**（金目当ての乗っ取り） |
| **顧客満足** | `client` | 50 | **契約解除**（損害賠償請求） | **際限なき奴隷**（過剰要求で現場崩壊） |
| **現場メンタル** | `dev` | 50 | **全員蒸発**（退職代行・一斉バックレ） | **技術オタク化**（売上無視で納期破綻） |
| **コンプラ** | `legal` | 50 | **労務監査局突入**（Web版：労働局突入 / 違法派遣摘発） | **官僚主義崩壊**（厳格すぎて案件ゼロ） |

2. **ゲームオーバー判定の優先順位（同時崩壊時）と死因バランシング指針：**
   * 同時に複数のパラメータが 0 または 100 に達した場合、以下の優先順位で死因を判定する。
     1. `cash`（下限 ＞ 上限）
     2. `legal`（下限 ＞ 上限）
     3. `dev`（下限 ＞ 上限）
     4. `client`（下限 ＞ 上限）
   * **死因バランス指針：** 上記優先順位（資金＞コンプラ＞現場＞顧客）による「黒字倒産ばかりで死ぬ」偏りを防止するため、カード効果設計において現場メンタルやコンプラが急激に振れるカードを意図的に配分し、全8種の死に様が満遍なく発生するようバランシングを行う。

3. **四半期・季節の固定イベント（定例イベント / ボス戦）：**
   * 完全ランダムだけでなく、以下の特定週でSES業界特有の重要イベントが必ず発生する。
     * **Week 13（春）：** 「新卒・未経験の現場配属ラッシュ」（メンタル激減 vs 資金獲得）
     * **Week 26（夏）：** 「賞与査定＆中間決算」（資金大幅減 vs メンタル維持）
     * **Week 39（秋）：** 「下期体制変更＆炎上案件の火消し要請」（客先無茶振り）
     * **Week 52（冬）：** 「年度末納品デスマーチ＆総決算」（最後の難関）

4. **社長の超法規的決断（1プレイ1回限りの切り札スキル）：**
   * 通常の2択とは別に、絶望的な状況を打破する「切り札ボタン」を画面下に配置（52週中1度だけ発動可能）。
   * 発動すると経営スタイルに応じた強力な効果をもたらすが、重い代償を伴う。

5. **売上スコア（`totalSales`）の算出仕様：**
   * 経営成績として、ターン経過および選択肢の `cash` 増加分を累積して算出。
   * 計算式：`累積売上（万円） = (生存週数 × 200) + (現資金 cash × 10)`

6. **ゲーム進行・生存カーブ・テンポ設計（1ターン）：**
   * **段階的な生存カーブ設計（リプレイ中毒性のコア）：**
     * **初見プレイ：** 平均生存週数を **Week 8〜15（約30〜45秒）** に設定。最初の数手で理不尽に撃沈させ、「なんじゃこれw」という自虐とリトライ意欲を最大化する。
     * **2〜3回目：** Week 26（夏の賞与・中間決算）の壁に直面させ、リソース管理の重要性を学習させる。
     * **4〜6回目以降：** 切り札スキルと季節イベント対策を駆使して、ようやく「Week 52完走」が見える階段状の難易度カーブを設計。
   * **テンポ感設計：**
     * カード選択後のアニメーション待機時間・トランジションは **0.3秒以下** とし、サクサク進む手触りを保証。
   * **カードドロー優先順位：**
     1. 当該週が `fixed_week` と一致する固定イベントが存在する場合、それを最優先で表示（山札を消費しない）。
     2. 該当週に連鎖注入予約（後述）があれば、その注入カードを山札の先頭に挿入した上でドロー。
     3. 上記に該当しなければ通常山札からドロー。
   * プレイヤーは［選択肢A（左スワイプ / 左キー / 左ボタン）］または［選択肢B（右スワイプ / 右キー / 右ボタン）］を選択。
   * **効果値の演算順序（明文化）：**
     1. 選択肢の基礎効果値（`ChoiceEffect`）に、経営スタイルのパッシブ倍率を乗算する。倍率は「増加方向・減少方向どちらの効果にもその符号のまま乗算」する。
     2. 複数のパッシブ倍率が同一パラメータに影響する場合は、定義順（資金→顧客満足→現場メンタル→コンプラの順）に**逐次乗算**する。
     3. 乗算後の値を `Math.round` で整数化してから4大パラメータへ加算/減算する（丸めは最終値1回のみ）。
   * **連鎖カード注入判定：** 選択肢に `inject_card_id` が設定されている場合、`pendingInjections` キューに `{targetWeek, cardId}` を追加する。
   * 週カウントが `+1` され、ゲームオーバー判定を経て次のターンへ。

### 3.2 イベントカード＆連鎖システム（Store-Safe Mode対応）

* **山札管理仕様：**
  * ゲーム開始時に通常カード（連鎖・季節固定カードを除く）をシャッフルした「山札」を作成。連鎖カード・季節固定イベントは通常山札には含めず、別管理とする。
  * **ミニ連鎖（山札注入システム）：**
    * プレイヤーの決断によって、`pendingInjections` キューに「対象週＋カードID」を予約登録。対象週に到達した時点で山札の先頭に挿入する。
    * 例：Week 5に「未経験者の経歴をJava歴3年に盛る」を選択 → 対象週（Week 8〜15の間でランダムに1週決定）に「現場でボロが出て客先激怒」カードを自動注入。
  * 山札が尽きた場合は、**使用済みの通常カードのみ**を再シャッフルして山札を再構築する（フリーズ防止）。
* **MVPカード数要件：**
  * MVP（Phase 1）リリース時点で**最低60枚**（通常50枚＋連鎖・季節10枚）を実装。
  * 正式リリース（Phase 2）時点で**100枚**へ拡充。
* **データ構造（TypeScript型定義 / ストア審査セーフテキスト対応）：**

```typescript
export interface ChoiceEffect {
  cash: number;   // -100 ~ 100
  client: number; // -100 ~ 100
  dev: number;    // -100 ~ 100
  legal: number;  // -100 ~ 100
}

export interface Choice {
  text: string;
  text_store_safe?: string; // ストア審査用マイルドテキスト（例: "経歴プロデュースで現場へ"）
  effects: ChoiceEffect;
  inject_card_id?: string; // 選択後に山札へ混入させる後続イベントカードID
}

export interface EventCard {
  id: string;
  speaker_name: string;
  speaker_icon: string; // 例: "icon_sales.webp"
  message: string;
  message_store_safe?: string; // ストア審査用マイルドテキスト（NGワード回避用）
  choice_left: Choice;
  choice_right: Choice;
  fixed_week?: number; // 季節固定イベントの場合に指定（例: 13, 26, 39, 52）
}

// 連鎖カードの注入予約（山札本体とは独立管理）
export interface PendingInjection {
  targetWeek: number; // 注入対象週
  cardId: string;
}

// 称号判定・ラン中の継続状態を保持するランタイム専用ステート
export interface RuntimeGameState {
  currentWeek: number;
  parameters: ChoiceEffect;
  minLegalDuringRun: number;
  maxCashDuringRun: number;
  usedTrumpCard: boolean;
  pendingInjections: PendingInjection[];
}
```

### 3.4 リザルト＆SNSバイラルエンジン（摩擦ゼロ拡散仕様）

1. **動的画像生成（倒産報告書 / 決算通知書）：**
   * ゲーム終了時、画面上のHTMLテンプレートを `html-to-image` でPNG画像（Base64/Blob）に変換。
   * **印字項目：** 会社名、生存週数、経営スタイル、結末名、獲得称号、最終売上。

2. **摩擦ゼロ・X（Twitter）タイムライン画像自動展開仕様：**
   * 手動画像保存・手動添付による拡散離脱（90%削ぎ落とし）を完全に防ぐため、**全8種の死因＋クリアに対応する静的OGP個別ページ（または動的OGPルーティング）** を整備する。
     * 例：`https://genkai-ses.pages.dev/results/dev-zero`（「全員蒸発エンド」の一枚絵カードOGPが埋め込まれたURL）
   * ［Xで末路を晒す］ボタンを押すだけで、ユーザーが画像を手動添付しなくても、**タイムライン上に該当する死に様の一枚絵がドカンと自動表示される**仕組みを実現。
   * モバイル環境では Web Share API（画像Blob直接添付）も同時サポート。

3. **バイラルを最大化するシェア定型文（挑戦状＆比較フック）：**

## 4. UI/UX・アセット要件

### 4.1 画面デザイン・操作設計

* **トーン：** Slack / Discord 風のダークモードビジネスUI（ダークグレー `#1E1F22`, ターミナルグリーン `#22C55E`, 警告レッド `#EF4444`）。
* **フォント：** 等幅フォント（`JetBrains Mono`, `Fira Code`, `ui-monospace` 系）を採用。
* **入力・操作仕様（ハイブリッド両対応）：**
  * **キーボード操作：** `←`（左選択） / `→`（右選択） / `Space`（切り札発動）
  * **スワイプ操作：** `framer-motion` によるカードの左右ドラッグ/フリック
  * **ボタン操作：** 画面下の「選択肢A / 選択肢B」および「切り札発動」ボタン

## 7. 補足・実装ガイドライン（Implementation & Non-Functional Guidelines）

### 7.1 UX & ゲームフィール設計
1. **パラメータ変動の予兆（Preview Indicator）演出：**
   * カードを左右にドラッグ（傾き）した際、選択した場合に影響を受けるパラメータ（`cash`, `client`, `dev`, `legal`）のアイコン上部にインジケータ（点滅ドット）を表示。
2. **サウンド仕様方針：**
   * アセット不要な Web Audio API（軽量シンセ発振器）による効果音（めくり音、倒産音、切り札発動音、クリアファンファーレ）をオプション実装（`sound_enabled` でON/OFF）。

### 7.2 セキュリティ・法務・データバリデーション
1. **会社名入力のサニタイズ・バリデーション：**
   * 最大15文字制限、HTML特殊文字の自動エスケープ、未入力時『限界SES株式会社』フォールバック。
2. **実在企業・商標の完全排除ルール（知的財産保護）：**
   * カードメッセージ内では実在の企業名・サービス名・特定の商標（またはそれを想起させる隠語）を完全に排除し、徹底して「役職・ステレオタイプ（元請けPM、客先役員、新人プログラマ等）」の行動様式のみを描写する。
3. **途中進行セッションの保護（誤リロード・離脱対策）：**
   * 1ターン終了ごとに現在のプレイ状態（週数、パラメータ、山札・使用カード、切り札使用フラグ）を `sessionStorage` に自動退避し、リロード時に「続きから再開」を提供。
4. **Storage例外ハンドリング：**
   * Safariプライベートモード等での読み書き例外をtry-catchし、失敗時はインメモリオブジェクトでセッション中のみデータを保持するフォールバックを導入。
   * ストレージアクセスは前述の`SaveRepository`インターフェース内に集約し、例外処理をそこに一元化する。

### 7.3 Webパフォーマンス & Cloudflare Pages運用
1. **SPAルーティング設定：**
   * `public/_redirects` に `/* /index.html 200` を配置し、ページ直接アクセスやリロード時の404エラーを防止。
2. **静的アセットの長期キャッシュ：**
   * `public/_headers` にて、静止画アセット（`/assets/*.webp`）に対して `Cache-Control: public, max-age=31536000, immutable` を設定。
3. **`html-to-image` 描画安定化処理：**
   * 画像生成直前に `document.fonts.ready` を待機し、フォント読み込み完了を保証した上でCanvas変換を行う。
   * `html-to-image` はiOS Safariで背景画像・独自フォントのレンダリングに既知の制約があるため、**iOS Safari実機での画像生成検証はWeek4（MVP完成時点）で先行実施**する。
4. **静止画アセットのプリロード失敗時挙動：**
   * 17枚のWebPプリロード中に1枚でも取得失敗した場合、ゲーム起動をブロックせずプレースホルダー画像で代替表示し、エラーログを出力。

### 7.4 規約・ストア審査対策 & アナリティクス完全網羅
1. **法的表記・AdSense審査・ストア免責用モーダル：**
   * タイトル画面フッター等から「遊び方」「利用規約 / プライバシーポリシー / 免責事項（フィクション表記）」「お問い合わせ」モーダルを配置。
2. **ストア審査用テキスト切り替え機構（Store-Safe Mode）：**
   * ネイティブアプリ申請時は、環境変数（例: `VITE_APP_STORE_SAFE_MODE=true`）の切り替えにより、カードテキストおよびUI文言を `message_store_safe` / `text_store_safe` にフォールバックする仕組みを組み込む。
3. **Apple審査提出用 Review Notes 準備方針：**
   * 審査提出時に以下の趣旨の英文説明を添付する：
     * *"This game is a fictional business satire simulation. Actions violating legal regulations in the game always lead to immediate bankruptcy (Compliance Failure Game Over), demonstrating the moral hazard of unethical management practices."*
