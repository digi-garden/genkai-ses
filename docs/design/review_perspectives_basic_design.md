# 基本設計 レビュー観点

> 作成日：2026-10-31 ／ 対象：`docs/design/00〜10`（基本設計 v1.0 一式）と `docs/requirements_v1.12.md`
> 目的：基本設計を、実装に入る前に必要十分な観点で確認する。観点ごとに、見る資料・向いているレビュアー・重点の問いを示す。

---

## 1. レビューの考え方

- 要件定義のレビュー（第1〜5回）で「何を作るか」は固まった。基本設計のレビューでは、主に次の3点を確かめる。
  1. **要件どおりか**（漏れ・食い違いがないか）
  2. **このまま作れるか**（実装者が迷わないか、工数に収まるか）
  3. **作った後に困らないか**（テスト・運用・法務・性能）
- 資料が多いので、観点ごとに**見る資料を絞って**依頼する。1回のレビューで全資料・全観点を見てもらうと、指摘が浅くなる。
- 設計者（Claude）が**自分で懸念している点**を 4章に挙げた。レビュアーには、ここを優先して突いてもらう。

## 3. レビューの進め方（おすすめ）

| 回 | 観点 | レビュアー | 渡すもの |
|---|---|---|---|
| ① | V5・V6（画面と見た目） | **オーナー自身** | `mockup/index.html`（または `10_mockup.md` の画像一覧）、02、03 |
| ② | V1・V2（要件との対応、資料の整合） | 外部AI | 要件書 v1.12、00〜09 の全文 |
| ③ | V3・V4・V9（ロジック、データ、テスト） | 外部AI | 要件書 v1.12、04、05、07 |
| ④ | V7・V8・V10・V11（技術、連携、性能、セキュリティ・法務） | 外部AI | 要件書 v1.12、01、06、08、09 |
| ⑤ | V12・V13（運用、工数） | 外部AI ＋ オーナー | 要件書 v1.12、00、07、08（＋ ②〜④ の結果） |

- **① を最初にする理由：** 画面と見た目は、ゲームの手触りに直結し、オーナーの好みや狙いで決まる部分が大きい。外部AIは画像を渡さないと見られないこともあり、まずオーナーが確かめるのが早い。
- **② を早めにする理由：** 要件との漏れや資料間の食い違いは、後の回の指摘の前提を崩すため。
- **⑤ を最後にする理由：** ②〜④ で直す内容によって工数が変わるため。
- 外部AIに画面を見てもらう場合は、`mockup/screens/*.png` を添付する。

## 5. 依頼文の雛形（外部AI用）

```
あなたは Web フロントエンドとゲーム開発の経験が豊富なレビュアーです。
個人開発の Web ゲーム「限界SES社長」の基本設計書をレビューしてください。

# 前提
- Reigns 型の業界風刺シミュレーション。React + TypeScript の SPA で、サーバーを持たず Cloudflare Pages で静的に配信する。
- 開発は個人で、総工数40〜60時間・8週間。
- 要件定義は5回のレビューを経て確定済み（requirements_v1.12.md）。要件そのものへの指摘は、設計に影響する重大なものだけにしてください。
- 設計で要件を変えた点・補った点は、00_index.md の3章にまとめています。

# 観点
review_perspectives_basic_design.md の観点 [ここに番号を記入。例：V3, V4, V9] を中心に見てください。
同じファイルの4章「設計者が自分で懸念している点」のうち、関係するものは必ず評価してください。
観点リストにない問題に気づいた場合も挙げてください。

# 出力形式
指摘ごとに、次の項目を書いてください。
- 重要度：高（実装に入れない、または作り直しになる）／中（品質や工数に大きく影響する）／低（改善提案）
- 該当箇所（資料番号と章。例：04 の 6.3）
- 問題点（何が・なぜ問題か）
- 改善案（具体的に。複数案ある場合は推奨案を明示）
4章の懸念点については、「問題なし／要対応」と理由を書いてください。
最後に、この設計で「実装に進めてよいか」を「可／条件付きで可／不可」で答え、条件付き・不可の場合はその条件を挙げてください。
```

- 返ってきた指摘は、これまでと同じく採否と理由を整理し（`docs/design/review_bd_r{回}_triage.md`）、設計書と、必要なら要件書 v1.13 に反映する。
