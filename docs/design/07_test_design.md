# 07 検証・テスト設計書

> 版：1.0（2026-10-31） ／ 対象要件：`requirements_v1.12.md`（7.5、7.3-3） ／ 関連：`04_game_logic.md`、`05_data_design.md`
> 目的：バランスと品質を、手作業に頼らずに確かめる。手作業の確認は、実機でしか分からないことに絞る。

## 1. テストの方針

| 層 | 手段 | 対象 | いつ実行するか |
|---|---|---|---|
| ① データ検証 | `validate:cards` | カード JSON（05 の 3.4、V1〜V13） | ビルドのたび、CI |
| ② 単体テスト | Vitest | `core` の全関数、`infra` の一部（シェア文の組み立て、文字数の計算、NG 社名の判定、SaveData の移行） | CI、手元で随時 |
| ③ シミュレータ | `npm run simulate` | ゲーム全体のバランス（要件 7.5） | カードを変更したとき、CI（ラン数を減らした版） |
| ④ E2E テスト | Playwright | 画面をまたぐ主要な流れ | CI |
| ⑤ 手動確認 | チェックリスト（6章） | 実機での操作感、画像生成、共有シート、OGP の表示 | Week 4（MVP）と Week 8（正式リリース）の前 |

- **重点は ② と ③。** ゲームの面白さとバランスが成否を分けるので、ルールの正しさ（②）と数値の妥当性（③）を自動で確かめ続ける。
- 画面のコンポーネント単体のテストは書かない（工数に見合わないため）。画面は ④ と ⑤ で確認する。

## 2. 単体テスト（Vitest）

### 2.1 対象と観点

| 対象 | 主な観点 |
|---|---|
| `effects.ts` | パッシブ倍率は名前の方向だけに掛かる。逐次乗算。符号付き四捨五入（-2.5 → -3、2.5 → 3）。クランプ |
| `deck.ts` | 初回は opening が先頭に来る。2回目以降は未読が先頭。スタイル別カードは選んだスタイルのものだけ入る（テスト用のカードデータで確認する。本物のスタイル別カードは Phase 2）。再シャッフル。同じシードなら同じ順番 |
| `turn.ts` | 要件 3.1-6 の処理順。極値の記録は Week 14 以降だけ。`cashGainedTotal` はクランプ前の増加分 |
| 連鎖 | 予約週の計算。衝突時に後ろへずれる。Week 52 超えで破棄。1ランに1回まで |
| 切り札 | 倍率なし、週が進まない、即死あり、使用済みなら何も起きない、グレー派遣の切り札は連鎖を予約する |
| `judge.ts` | 死因の優先順位、敗因の判定（3ターン以内・向き）、売上、称号6種（境界値：65 と 64、40 と 41、9週と10週） |
| `step` | 04 の 11章の境界条件 **E1〜E15 をすべてテストケースにする** |
| シェア文 | 3行目・4行目の有無、文字数の調整の5段階、注記とハッシュタグが必ず残る。最悪のケースで、投稿画面の URL 全体が 2,000文字以内（06 の 3.2） |
| `weightedLength` | 英数字＝1、全角＝2、URL＝23 |
| NG 社名の判定 | 全角半角、大文字小文字、空白、「株式会社」「(株)」の正規化。`@` `#` URL の検出 |
| SaveData の読み込み | 壊れた JSON、古い版からの移行、新しすぎる版、存在しないカード ID の除去 |

### 2.2 合格の基準
- `core` の行カバレッジ 90% 以上。
- すべてのテストが通ること（CI でプルリクエストのマージ条件にする）。

## 3. シミュレータ（`npm run simulate`）

### 3.1 実行のしかた

```
npm run simulate -- [--runs 10000] [--seed 1] [--bot random,greedy,gambler,greedy:white,greedy:bicycle]
                    [--style all] [--quick] [--json out.json] [--balance balance.override.json]
```

| オプション | 意味 | 既定値 |
|---|---|---|
| `--runs` | Bot × スタイルの組み合わせごとのラン数 | 10000（`--quick` のときは 1000） |
| `--seed` | 乱数の起点（ラン i のシード＝ `seed * 1000003 + i`） | 1 |
| `--bot` | 使う Bot | 3種すべて |
| `--style` | スタイル | 3種すべて |
| `--balance` | 閾値や係数を上書きするファイル（05 の 4.3 `balance.ts` の値） | なし |
| `--json` | 結果を JSON で書き出す | なし |

- 合計 9万ラン（3 Bot × 3スタイル × 1万）を、数十秒以内で終えることを目標にする（1ランは最大52ステップの純粋関数なので、十分に速い）。

### 3.2 Bot の動き（要件 7.5-3 を、実装できる粒度に詳しくしたもの）

| Bot | 選び方 | 切り札 | 初回プレイ扱い |
|---|---|---|---|
| `random` | 左右を 1/2 ずつで選ぶ | 毎ターン 3% の確率で使う（使える間） | **あり**（導入カードと opening のカードを使う。初見の生存カーブを測るため） |
| `greedy` | 両方の選択肢について、適用後の4パラメータの「50 からの距離の最大値」を計算し、小さい方を選ぶ。同じなら乱数で決める | いずれかのパラメータが 15 以下または 85 以上になったとき、切り札を使った後の「50 からの距離の最大値」が今より小さくなり、かつ即死しないなら使う | なし（全カード既読として扱う） |
| `gambler` | 適用後の `cash` が多い方を選ぶ。同じなら `greedy` と同じ基準で選ぶ | `greedy` と同じ | なし |
| `greedy:white` | `greedy` と同じ計算を、目標を 50 ではなく **コンプラ 80・ほかは 50** にして行う（目標からの距離の最大値が小さい方を選ぶ） | `greedy` と同じ（目標からの距離で判定） | なし |
| `greedy:bicycle` | 目標を **資金 25・ほかは 50** にした `greedy` | 同上 | なし |

- Bot は、プレイヤーが画面で見られる情報（予兆ドットの大小）ではなく、効果の正確な値を使う。人間より上手いので、`greedy` のクリア率は「上級者の上限」とみなす。

### 3.3 出力

```
=== 生存週数（中央値 / 平均 / p10 / p90） ===
random   tk: 11 / 13.2 / 5 / 24   gb: …   tf: …
greedy   …
=== 死因の比率（random + greedy） ===
cash_zero 18.2%  legal_zero 15.1% …  （上限死の合計 17.4%）
=== クリア率（greedy） ===  tk 24.1%  gb 21.8%  tf 27.0%  （差 5.2pt）
=== 称号の取得率 ===  …
=== 合格判定 ===
[OK] random の生存週の中央値が 8〜15        11
[NG] 下限死 legal_zero が 5〜25%            26.3%
…
```

- 生存週数のヒストグラム（1週ごと）も、JSON に出力する。
- カードごとの「表示回数」と「そのカードのターンで倒産した回数」も出す（極端に危険なカードを見つけるため）。

### 3.4 合格基準（要件 7.5-4 と v1.10）

| # | 基準 | 対象 |
|---|---|---|
| A1 | 生存週数の中央値が Week 8〜15 | `random`（初回プレイ扱い） |
| A2 | クリア率が 15〜35% | `greedy`（スタイルごと） |
| A3 | 下限死4種がそれぞれ 5〜25% | `random` と `greedy` の合算 |
| A4 | 上限死4種がそれぞれ 1〜15%、合計が 10〜30% | 同上 |
| A5 | スタイル別のクリア率の差が 10ポイント以内（Phase 1 はスタイル別カードなしで、パッシブと切り札だけの差を見る） | `greedy` |
| A6 | 称号（クリア系4種）の取得率が、**その称号を狙う Bot** でクリアしたランの 1% 以上 | 『ホワイト企業の鑑』＝`greedy:white`、『自転車操業マスター』＝`greedy:bicycle`、『人月搾取の帝王』＝`gambler`、『不死鳥社長』＝`greedy` |
| A7 | 称号（スピード退職・監査局の常連）の取得率が、全ランの 0.5% 以上 | `random` |

- A7 は、要件 7.5-4 の「`random` の全ランで判定」に対して、具体的な下限値（0.5%）を定めたもの。
- **A6 で称号ごとに Bot を分ける理由（基本設計レビュー第2回の指摘2）：** `greedy` は4つのパラメータを 50 付近に保とうとするので、50 から離れた状態を保つことが条件の称号（コンプラ 65 以上、資金 40 以下、売上 1億）は、構造的にほぼ取れない。その称号を狙うプレイヤーの代わりとして、目標値をずらした `greedy`（`greedy:white`、`greedy:bicycle`）と `gambler` で判定する。目標値は、称号の閾値より少し内側（コンプラ 80、資金 25）に置く。
- A2〜A5 は、引き続き `greedy`（目標 50）で判定する。目標をずらした Bot は、A6 の判定だけに使う。
- 1つでも NG なら、終了コード 1 を返す。CI では警告として表示し、マージは止めない（01 の 7.2）。

### 3.5 調整の進め方
1. カードを書く（またはまとめて直す）。
2. `npm run simulate -- --quick` で傾向を見る。
3. NG の基準について、「カードごとの倒産回数」を見て原因のカードを探し、効果値を直す。全体の傾向がずれているときは `balance.ts`（倍率・閾値・売上の係数）を直す。
4. すべて OK になったら、`--runs 10000` で確認し、結果の JSON を `docs/balance/` に保存してコミットする（調整の記録として残す）。

## 4. E2E テスト（Playwright）

### 4.1 テスト用の仕組み
- 開発用とテスト用のビルド（`VITE_E2E=true`）でだけ、URL の `?seed=123` でシードを固定できるようにする。本番のビルドでは、この機能を含めない。
- テスト用のカードデータ（`tests/fixtures/cards/`）に差し替えるビルドは作らない。本物のカードとシードの組み合わせで、決まった展開を再現する。

### 4.2 シナリオ

| # | シナリオ | 確認すること |
|---|---|---|
| T1 | 初回の流れ：タイトル → 会社名（空欄）→ スタイル選択 → プレイ | 会社名が「限界SES株式会社」になる。Week 1〜2 に導入カードが出る |
| T2 | キーボードだけで5ターン進める | `←` `→` で週が進む。ゲージが変わる |
| T3 | 再読み込みからの再開 | 3ターン後に再読み込み → 「続きから再開（第4週）」→ 同じカードが出る |
| T4 | 切り札の2段階操作 | 1回目で確認表示、`Esc` で取り消し、2回目で発動し「使用済み」になる |
| T5 | 倒産まで進める（倒産するシードを使う） | リザルトに結末名・売上・注記が出る。［もう1期挑む］で会社名入力に戻り、前回の名前が入っている |
| T6 | 会社名のエラー | `@abc`、URL、NG 社名でエラーが出て先に進めない |
| T7 | 図鑑 | 倒産した結末が「？？？」から解放される |
| T8 | 結末ページ | `/results/dev-zero/` に OGP のタグがある。ボタンで `/` に移動する |
| T9 | X への投稿 | ［Xでポスト］で開く URL の `text` が280文字以内（06 の 3.2）で、`url` に utm が付いている（実際には開かずに URL を検査する） |

- **実施する時期（基本設計レビュー第4回で工数を絞った）：**
  - **Phase 1（MVP）：T1、T3、T5、T8 だけ**を作る（開始、途中再開、リザルトまで、結末ページ）。壊れると遊べなくなる流れに絞る。
  - **Phase 2：** T2、T4、T6、T7、T9 を追加する。ゲームのルールの細部は、E2E ではなく単体テスト（2章）とシミュレータ（3章）で確かめる。
- ブラウザ：Chromium（PC 1280×800）と、スマホのエミュレーション（Chromium、390×844、タッチ有効）。Phase 2 で、CI に WebKit も追加する（GitHub Actions では WebKit をインストールできる）。
