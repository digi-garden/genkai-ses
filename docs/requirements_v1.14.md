### 1.1 Web版PoC判定基準（アプリ化ゲート条件 / Go-No-Go KPI）
Web版リリース後2〜4週間の実績データを基に、スマホアプリ化（iOS/Androidネイティブ開発）への追加投資を行うか否かを判断する厳格な定量的基準：

> **計測の原則（v1.12）：** 比率で判定する指標（2〜5）は、**分母と分子を同じ計測ツール（GA4）で取る**。ターゲット層は広告ブロッカーの利用率が高く、GA4 の数値は実数より少なく出る。分母を Cloudflare Web Analytics、分子を GA4 で取ると、比率が構造的に低く出て誤って No-Go と判定してしまうため。絶対数の指標（1）だけは、広告ブロッカーの影響を受けない Cloudflare Web Analytics で判定する。

1. **初期流通・シード獲得：** 公開1ヶ月で **10,000 UU 以上**（Qiita/Zenn開発秘話、Tech系コミュニティ、X特定クラスタへの投下によるオーガニック獲得）。
2. **有効プレイ成立率：** **60% 以上**（開始10秒での即時離脱を除外したユーザーのうち、**いずれかのプレイで**第13週（春イベント）以上に到達したユーザーの割合）。※v1.8：初見撃沈カーブ（Week 8〜15）とリプレイを前提とした設計に合わせ、プレイ単位ではなく**ユーザー単位**で判定する。
3. **即時リプレイ性：** 1人あたり平均プレイ回数 **2.5回 以上**（初回死亡後の「もう1回！」ループの成立）。
4. **継続率（リテンション）：** **D1リテンション 15% 以上** / **D7リテンション 5% 以上**（LocalStorage/Cookieによる再訪トラッキング）。
5. **シェア率：** リザルト到達者のうち、シェアボタンを押したユーザーの割合が **5% 以上**。
   * ※v1.12：v1.11 までの「K ≧ 0.2（シェア率 5% × 1投稿あたりの流入4人）」から変更。今の X はリンク付きの投稿を表示しにくくするため、一般ユーザーの投稿1件から平均4人が流入するという前提は過大である。そこで、プロダクト側で改善できる「シェア率」を判定に使う。
   * **K 値は参考指標**として記録する（`K = シェア率 × 1シェアあたりの流入数`）。1シェアあたりの流入数は、`utm_source=x&utm_medium=share` 付きの流入を GA4 で数え、GA4 の捕捉率（GA4 のユーザー数 ÷ Cloudflare Web Analytics の UU）で割り戻して推定する。

## 2. 開発・技術前提条件

* **開発リソース：** 週4〜8時間 × 8週間（総稼働：約40〜60時間）
* **開発体制：** 個人開発（AIコーディングエージェントによる実装）
* **ソース管理：** GitHub の `digi-garden/genkai-ses`（ゲーム専用の独立したリポジトリ。v1.13）。本番に公開するブランチは `develop`
* **技術スタック（v1.13 で基本設計の決定を反映。詳細とバージョンは `docs/design/01_architecture.md`）：**
  * **フロントエンド：** React 19 + TypeScript 6.0 + Vite（`base` は `/genkai-ses/`）
  * **スタイリング：** Tailwind CSS + Lucide React（アイコン）
  * **カードUI / アニメーション：** `motion`（framer-motion の現在の名前。スワイプ・ドラッグ・フリック対応）
  * **ホスティング：** **Cloudflare Pages**（ゲーム専用のプロジェクト）。公開 URL へのアクセスは、ブランド共通の Router Worker が Pages に転送する（8章）
  * **Node.js：** 24 系（ブランドの他リポジトリの CI に合わせる）
  * **データ永続化：** **LocalStorage のみ**（外部DB・サーバー構築は一切行わない）
  * **画像生成：** **`html-to-image`** によるクライアントサイドPNG生成
  * **アセット調達：** 生成AIによるドット絵静止画（計18枚・WebP形式。v1.14 で18枚に）
* **アーキテクチャ方針（将来のアプリ化移植を見据えて）：**
  * ゲームロジック（カード効果計算・パラメータ管理・ゲームオーバー判定・称号判定）は、UI（React コンポーネント）およびストレージ実装（LocalStorage / sessionStorage）から分離した純粋な関数群・モジュールとして実装する。
  * ストレージアクセスは直接 `localStorage.getItem/setItem` を呼ばず、`SaveRepository` インターフェース越しに行う（将来 React Native / Capacitor 移植時に AsyncStorage 等へ差し替え可能にするため）。

## 3. 機能要件（Functional Requirements）

### 3.1 ゲームコアロジック

1. **4大パラメータ管理：**
   * 各パラメータは `0〜100` の整数値で管理（初期値は各50）。
   * 変動時は `0 <= value <= 100` にクランプ（Clamp）処理を行う。
   * いずれかが「0」または「100」に達したターン終了時に**即ゲームオーバー**。
   * 全52ターン（1年間）生存で「1期完走（ゲームクリア）」。Week 52 のカードでパラメータが崩壊した場合は**死亡を優先**する（クリア扱いにしない）。
   * **死亡週の定義：** 「第N週に倒産」のNは、死亡したカード（または切り札を発動した週）の週番号。生存週数は `N−1`（クリア時は52）。
   * **ゲージ表示：** 数値は表示せず、ゲージの量だけで示す（Reigns方式）。

| パラメータ名 | 英語表記 | 初期値 | 0になった時（下限死） | 100になった時（上限死） |
| :--- | :--- | :--- | :--- | :--- |
| **資金** | `cash` | 50 | **黒字倒産**（入金ズレで資金ショート） | **買収・内紛**（金目当ての乗っ取り） |
| **顧客満足** | `client` | 50 | **契約解除**（損害賠償請求） | **際限なき奴隷**（過剰要求で現場崩壊） |
| **現場メンタル** | `dev` | 50 | **全員蒸発**（退職代行・一斉バックレ） | **技術オタク化**（売上無視で納期破綻） |
| **コンプラ** | `legal` | 50 | **労務監査局突入**（監査の立ち入りで事業停止） | **官僚主義崩壊**（厳格すぎて案件ゼロ） |

2. **ゲームオーバー判定の優先順位（同時崩壊時）と死因バランシング指針：**
   * 同時に複数のパラメータが 0 または 100 に達した場合、以下の優先順位で死因を判定する。
     1. `cash`（下限 ＞ 上限）
     2. `legal`（下限 ＞ 上限）
     3. `dev`（下限 ＞ 上限）
     4. `client`（下限 ＞ 上限）
   * **死因バランス指針：** 上記優先順位（資金＞コンプラ＞現場＞顧客）による「黒字倒産ばかりで死ぬ」偏りを防止するため、カード効果設計において現場メンタルやコンプラが急激に振れるカードを意図的に配分し、全8種の死に様が満遍なく発生するようバランシングを行う。※v1.10：下限死（0到達）を主な死因とし、上限死（100到達）は「狙わないと出にくい、やや希少な死に様」として位置づける（合格基準は 7.5）。

3. **四半期・季節の固定イベント（定例イベント / ボス戦）：**
   * 完全ランダムだけでなく、以下の特定週でSES業界特有の重要イベントが必ず発生する。
     * **Week 13（春）：** 「新卒・未経験の現場配属ラッシュ」（メンタル激減 vs 資金獲得）
     * **Week 26（夏）：** 「賞与査定＆中間決算」（資金大幅減 vs メンタル維持）
     * **Week 39（秋）：** 「下期体制変更＆炎上案件の火消し要請」（客先無茶振り）
     * **Week 52（冬）：** 「年度末納品デスマーチ＆総決算」（最後の難関）

4. **社長の超法規的決断（1プレイ1回限りの切り札スキル）：**
   * 通常の2択とは別に、絶望的な状況を打破する「切り札ボタン」を画面下に配置（52週中1度だけ発動可能）。
   * 発動すると経営スタイルに応じた強力な効果をもたらすが、重い代償を伴う。
   * **発動ルール（v1.8）：**
     * ターンは消費しない。現在のカードを表示したまま即時に適用し、適用後は同じカードの2択に戻る。季節固定イベントの週でも発動できる。
     * 切り札の効果値は固定値で、**パッシブ倍率は掛けない**。
     * 適用後、**直ちに死亡判定を行う（即死あり）**。いずれかが0または100に達した場合は、通常と同じ優先順位で死因を決めてゲームオーバーにする。
     * **予兆表示：** 確認状態（下記）の間は、通常カードのドラッグ時と同じ**予兆ドット**（7.1-1）をゲージに表示する。即死するかどうかは明示しない（⚠などの確定情報は出さない）。
     * **発動操作（v1.10。危険かどうかにかかわらず、毎回2段階）：**
       * **1回目**（タップ、クリック、または `Space`）：切り札ボタンが**確認状態**になる（点滅・発光）。予兆ドットを表示し、ボタンの上に「この決断は取り返しがつきません。もう一度押すと実行」と表示する。
       * **2回目**（確認状態の切り札ボタンをもう一度タップ、クリック、または `Space`）：発動する。
       * **取り消し：** `Esc`、切り札ボタン以外の場所をタップ・クリック、カードのドラッグ開始、または2択ボタン・`←` `→` の操作。取り消すと確認状態と予兆ドットを解除する。2択の操作は、取り消しと同時にそのまま選択として受け付ける。
       * **PC のホバー：** 確認状態でなくても、ホバー中は予兆ドットを表示する（プレビューだけ）。
       * **長押しはトリガーにしない**（モバイルでのテキスト選択やコンテキストメニューの誤発火を避けるため）。ボタンには `user-select: none` と `-webkit-touch-callout: none` を指定する。
       * 確認状態の表示切り替えは、テンポの要件（0.3秒以下）の対象とする。

5. **売上スコア（`totalSales`）の算出仕様：**
   * 経営成績として、ターン経過および選択肢の `cash` 増加分を累積して算出する。
   * 計算式：`累積売上（万円） = (生存週数 × 100) + (cashGainedTotal × 50)`
     * `cashGainedTotal`：ラン中に**選択肢と切り札で `cash` が増えた量**（パッシブ倍率と丸めの後、クランプ前の値）の正の値だけの合計。減少分は差し引かない。
     * 試算：クリアだけで 5,200万。『人月搾取の帝王』（1億）には `cashGainedTotal >= 96` が必要。係数はバランス調整（Phase 1 Week 4）で最終決定する。
     * ※v1.7 の式（`週×200 + cash×10`）はクリア時に必ず1億を超え、称号が自動で取れてしまうため v1.8 で変更。

6. **ゲーム進行・生存カーブ・テンポ設計（1ターン）：**
   * **段階的な生存カーブ設計（リプレイ中毒性のコア）：**
     * **初見プレイ：** 平均生存週数を **Week 8〜15（約30〜45秒）** に設定。最初の数手で理不尽に撃沈させ、「なんじゃこれw」という自虐とリトライ意欲を最大化する。
     * **2〜3回目：** Week 26（夏の賞与・中間決算）の壁に直面させ、リソース管理の重要性を学習させる。
     * **4〜6回目以降：** 切り札スキルと季節イベント対策を駆使して、ようやく「Week 52完走」が見える階段状の難易度カーブを設計。
     * **実現方式（v1.8）：** 適応的な難易度調整は行わない。初回プレイだけ「序盤カード（`opening: true`）」を優先して引かせ（山札の構築手順 2）、2回目以降は通常の抽選にする。2〜3回目の Week 26 の壁は、季節固定イベントの効果量で作る。カーブが成立しているかは、ヘッドレスシミュレータの合格基準（7.5）で検証する。
   * **テンポ感設計：**
     * カード選択後のアニメーション待機時間・トランジションは **0.3秒以下** とし、サクサク進む手触りを保証。
   * **カードドロー評価順（v1.10。上から順に評価し、最初に該当したものを表示する）：**
     1. **初回プレイ（`play_count == 0`）かつ Week 1〜2：** 導入カード（`kind: 'tutorial'`）を表示する（山札を消費しない）。
     2. **当該週が `fixed_week`（13 / 26 / 39 / 52）と一致：** 季節固定カードを表示する（山札を消費しない）。
     3. **当該週を対象とした連鎖注入予約（`pendingInjections`）がある：** その連鎖カードを表示する（山札を消費しない）。注入週の衝突ルール（3.2）により、2と3が同じ週に重なることはない。
     4. **上記以外：** 通常山札の先頭からドローする。山札が空なら、使用済みの通常カードを再シャッフルして山札を作り直してからドローする。
   * **山札の構築手順（v1.10。ゲーム開始時に1回だけ行う）：**
     1. 対象カード＝ `kind: 'normal'` のうち、`style_only` が未指定のもの、または選択した経営スタイルと一致するもの。
     2. **初回プレイ：** 山札＝［`opening: true` のカードをシャッフル］＋［それ以外をシャッフル］。
     3. **2回目以降：** 山札＝［未読カード（`seen_card_ids` にないもの）をシャッフル］＋［既読カードをシャッフル］。`opening` フラグは無視する。
     4. 山札切れで再シャッフルするときは、未読・既読・`opening` を区別せず、使用済みの通常カードをまとめてシャッフルする。
     5. カードを画面に表示した時点で、そのIDを `seen_card_ids` に追加する（導入・季節固定・連鎖カードを含む）。
   * プレイヤーは［選択肢A（左スワイプ / 左キー / 左ボタン）］または［選択肢B（右スワイプ / 右キー / 右ボタン）］を選択。
   * **効果値の演算順序（明文化）：**
     1. 選択肢の基礎効果値（`ChoiceEffect`）に、経営スタイルのパッシブ倍率を乗算する。**倍率は名前に示された方向の効果にだけ掛ける**（例：「現場メンタル減少 ×0.8」は dev が減るときだけ、「獲得資金 ×1.3」は cash が増えるときだけ）。乗算で符号は変わらない。
     2. 複数のパッシブ倍率が同一パラメータの同一方向に影響する場合は、定義順（資金→顧客満足→現場メンタル→コンプラ）に**逐次乗算**する。
     3. 乗算後の値を**符号付き四捨五入**（0.5 は0から遠い方へ。`Math.sign(x) * Math.round(Math.abs(x))`）で整数化してから加算する（丸めは最終値1回のみ）。※`Math.round(-2.5) = -2` となる非対称を避けるため。
   * **1ターンの処理順（v1.8 で固定）：**
     1. カード表示（ドロー優先順位に従う）
     2. プレイヤーが選択（切り札は、選択前に任意で発動できる。3.1-4 参照）
     3. パッシブ倍率を掛ける
     4. 丸める
     5. 4大パラメータへ加算し、0〜100 にクランプする。`cashGainedTotal` を更新する
     6. 極値（`minLegalSinceQ2` / `maxCashSinceQ2`）を記録する（Week 14 以降のターンのみ）
     7. 連鎖注入を予約する：選択肢に `inject_card_id` があれば、`targetWeek = 現在週 + inject_delay の範囲からランダム` で `pendingInjections` に追加する。このとき、因果を表示するために、元の週（`originWeek`）と選択肢の `regret_text` も一緒に保存する
     8. **死亡判定**：0 または 100 に達したパラメータがあれば、優先順位に従って死因を決めてゲームオーバーにする
     9. 週カウントを `+1` する
     10. 週が52を超えていればクリア。そうでなければ sessionStorage へ退避して次のターンへ

### 3.2 イベントカード＆連鎖システム（Store-Safe Mode対応）

* **山札管理仕様：**
  * ゲーム開始時に通常カード（連鎖・季節固定カードを除く）をシャッフルした「山札」を作成。連鎖カード・季節固定イベントは通常山札には含めず、別管理とする。
  * **ミニ連鎖（山札注入システム）：**
    * プレイヤーの決断によって、`pendingInjections` キューに「対象週＋カードID」を予約登録。対象週に到達した時点で山札の先頭に挿入する。
    * 例：Week 5に「未経験者の経歴をJava歴3年に盛る」（`inject_delay: [3, 10]`）を選択 → 対象週（Week 8〜15の間でランダムに1週決定）に「現場でボロが出て客先激怒」カードを自動注入。
    * **注入週の指定：** 絶対週ではなく、選択した週からの相対週の範囲 `inject_delay: [min, max]` で指定する（省略時は `[2, 6]`）。
    * **衝突ルール：**
      * 注入する週が季節固定イベントの週と重なった場合は、翌週にずらす。
      * 同じ週に複数の注入が重なった場合は、予約した順に1週ずつ後ろへずらす（1週に注入するのは1枚まで）。
      * ずらした結果 Week 52 を超えた注入は破棄する。
      * 同じ連鎖カードが既に予約済みの場合は、重複して予約しない。
  * 山札が尽きた場合は、**使用済みの通常カードのみ**を再シャッフルして山札を再構築する（フリーズ防止）。
* **MVPカード数要件：**
  * MVP（Phase 1）リリース時点で**62枚**（通常の共通カード50枚＋連鎖6枚＋季節固定4枚＋導入2枚）を実装する。**スタイル別カード15枚は Phase 2（Week 5）で追加する**（v1.13。工数の試算が上限を超えたため。未読カードの優先ドローにより、62枚でもリプレイ性を保てる）。
  * 正式リリース（Phase 2）時点で**100枚以上**へ拡充。
  * 内訳（MVP）：
    * 通常の共通カード50枚。このうち**序盤カード（`opening: true`）を8枚以上**含める。
    * **スタイル別カード15枚**（各経営スタイル5枚。`style_only` を指定する）。1ランで山札に入るのは、共通50枚と自スタイル5枚の計55枚。
    * **削減ライン：** スケジュールが遅れた場合、最初に削るのはスタイル別カード（Phase 2 へ延期。その場合 MVP は計62枚）。未読カードの優先ドローだけは MVP に残す。
    * 連鎖カード6枚、季節固定カード4枚（各固定週に1枚）、導入カード2枚（初回プレイのみ）。
  * **ピンチカード**（いずれかのパラメータが危険域のときだけ山札に混ざるカード）は Phase 2 で導入を検討する。
  * **連鎖カードの因果表示（v1.9）：**
    * 連鎖カード（`kind: 'chain'`）を表示するときは、カード上部に「【因果応報】」バッジを付け、短い演出（効果音とアラート表示）を入れる。
    * 執筆ルール：連鎖カードの `message` の書き出しで、元になった過去の選択に言及する（例：「（あの時、経歴を盛った新人が…）」）。
    * **敗因の判定（v1.10）：** 次の両方を満たす場合、リザルト画面とシェア文に、元になった選択の `regret_text` を「敗因」として表示する（例：「敗因：第5週『新人の経歴をJava歴3年に盛った』」）。
      1. 直近に解決した連鎖カードのターンから**3ターン以内**（連鎖カードのターンを含む）に死亡した。
      2. その連鎖カードの効果が、**死因となったパラメータを死因の向きに動かしていた**（例：dev の下限死なら、連鎖カードの dev の効果がマイナスだった）。
      * 直近の連鎖カードだけを判定の対象にする。条件を満たさない場合は、結末ごとの定型コメントを表示する。
  * Phase 2 では、季節固定イベントを各週2〜3枚の候補に増やし、その中から抽選する（リプレイ時の単調さ対策）。
  * 全カードについて、8種の死因それぞれにつながる効果が偏りなく出るよう配分する（3.1-2 の死因バランス指針）。
* **データ構造（TypeScript型定義 / ストア審査セーフテキスト対応）：**

### 3.4 リザルト＆SNSバイラルエンジン（摩擦ゼロ拡散仕様）

1. **動的画像生成（倒産報告書 / 決算通知書）：**
   * ゲーム終了時、画面上のHTMLテンプレートを `html-to-image` でPNG画像（Base64/Blob）に変換。
   * **印字項目：** 会社名、生存週数、経営スタイル、結末名、獲得称号、最終売上。
   * **ゲームの URL の印字（v1.12）：** 画像の最下部に「限界SES社長」というタイトルと `promptlab-games.com/genkai-ses` を印字する（v1.13）。画像だけが単体で投稿されても、そこから流入できるようにするため。
   * **注記の強制表示（v1.11）：** 画像の下部に「※会社名はプレイヤーが入力した架空の名称です。本作はフィクションです。」を必ず印字する（7.2-1 参照）。

2. **摩擦ゼロ・X（Twitter）タイムライン画像自動展開仕様：**
   * 手動画像保存・手動添付による拡散離脱（90%削ぎ落とし）を完全に防ぐため、**全8種の死因＋クリアに対応する静的OGP個別ページ（または動的OGPルーティング）** を整備する。
     * 例：`https://promptlab-games.com/genkai-ses/results/dev-zero`（「全員蒸発エンド」の一枚絵カードOGPが埋め込まれたURL。v1.13）
     * **URL の形（v1.13）：** 末尾にスラッシュを付けない。結末ページは `results/{slug}.html` というファイルで出力する（ディレクトリ＋`index.html` にしない）。Cloudflare Pages は末尾スラッシュの有無をそろえるために相対パスでリダイレクトを返し、Router 経由では公開パス（`/genkai-ses`）が抜けてポータルの404になるため（`docs/design/09_tech_spike.md` 検証4）。
     * **実現方式（v1.8）：** X のクローラーは JavaScript を実行しないため、**ビルド時に結末9種ぶんの静的 HTML**（v1.13 で `/results/{slug}.html`。`og:image` は `end_{id}.webp` を元にした 1200×630 の PNG または JPEG）を生成する。動的 OGP（Functions）は使わない。
     * OGP 画像は結末ごとの共通の一枚絵とし、会社名や週数などの個人別の情報は載せない（個人別の情報は本文テキストと、Web Share で添付する画像で伝える）。
     * 人が `/results/{id}` にアクセスした場合は、その結末の紹介と［このブラック業界に挑む］ボタン（トップへ遷移）を表示する。
   * ［Xで末路を晒す］ボタンを押すだけで、ユーザーが画像を手動添付しなくても、**タイムライン上に該当する死に様の一枚絵がドカンと自動表示される**仕組みを実現。
   * モバイル環境では Web Share API（画像Blob直接添付）も同時サポート。
   * **環境別のシェア導線（v1.9）：**
     * **モバイル（v1.12 で変更）：** ［Xでポスト］（Web Intent。テキスト・URL・OGPカードが確実に入る）を**主ボタン**にする。`navigator.canShare({ files })` が true の環境では、副ボタンとして［画像付きでシェア］（Web Share API）を出す。
       * 理由：Web Share API で画像とテキスト・URLを同時に渡すと、共有先のアプリによってはテキストと URL が捨てられ、画像だけが投稿されることがある。URL が消えると、見た人がゲームにたどり着けない。
       * ［画像付きでシェア］を押したときは、共有シートを開く前に**シェア文（URL を含む）をクリップボードにコピー**し、「本文はコピー済みです。貼り付けて投稿してください」と表示する。
     * **PC など**：［Xでポスト］（Web Intent。OGPカードが表示される）の横に［画像をコピー］［画像を保存］を置き、「報告書の画像を貼るともっと自慢できます」という一文を添える。クリップボードに画像を書き込めないブラウザでは、［画像を保存］だけを表示する。

3. **バイラルを最大化するシェア定型文（挑戦状＆比較フック）：**
```text
【限界SES社長】
〇〇株式会社は、第24週に「全員蒸発エンド」で倒産しました（売上4,800万）。
```

### 3.6 カード執筆ガイドライン（風刺の鉄則）（v1.11 新設）
1. **矛先は常に構造に向ける：** 笑いの対象は、多重下請けの商流、人月での値付け、無茶な仕様変更、理不尽な発注者や制度とする。現場のエンジニア、新人、下請け、退職者の苦しみそのものを嘲笑しない。
2. **最大の道化はプレイヤー（社長）自身：** 社長がうまく搾取して勝つ話にはしない。目先の金に目がくらんで自業自得の目に遭う、間の抜けた経営者として描く。上限死・下限死の結末テキストも「社長の経営判断の結果」として書く（例：「全員蒸発」は辞めた社員を責めず、そこまで追い込んだ社長を描く）。
3. **違法・不正行為には必ず代償を付ける：** 偽装請負、経歴詐称、二重派遣など、違法・不正行為にあたる選択肢（`unethical: true`）には、必ず代償の連鎖カード（`inject_card_id`）と `regret_text` を付ける。連鎖カードは、コンプラまたは顧客満足を大きく下げる内容にする。その場で得をしても、後で必ずツケが回る構図をルールとして徹底する（シミュレータのカード検証で必須チェックする。7.5-2）。
4. **差別・ハラスメントの禁止：** 性別、年齢、国籍、出身、障害、容姿などの属性をネタにしない。パワハラ・セクハラの描写は、加害者側を批判的に描く場合に限る。
5. **実在のものを出さない：** 実在の企業名、サービス名、商標、それを想起させる隠語を使わない（7.2-2）。登場人物は役職とステレオタイプで描く。
6. **手法を教えない：** 違法行為の具体的な手口（書類の偽造方法など）は書かない。「やった」という事実と、その結果だけを描く。
7. **表現の確認：** カードを書き終えたら、上記1〜6について全カードを見直す（観点3の再レビュー）。
8. **露骨な違法用語を使わない（v1.13）：** 「偽装請負」「二重派遣」「経歴詐称」「スキル詐称」「違法派遣」「労基」などの言葉を、カード・UI・結末・称号・シェア文のどこにも直接書かない。業界の人がニヤリとする言い換え（例：「経歴をプロデュースする」「商流が深い」「監査の立ち入り」）で描く。行為の中身と代償の構造（3）は変えない。理由：同じドメインでブランドが Google AdSense の審査を受けており、ドメイン全体の評価に影響しうるため。カード検証（7.5-2）で、これらの語を NG ワードとして検出する。

## 5. マネタイズ＆ユニットエコノミクス要件

### 5.1 Web版（PoCフェーズ）
* **v1.11：Web版PoCでは広告を一切置かない**（Google AdSense の実装をスコープから外す）。
  * 理由：違法行為を題材にした風刺ゲームは、AdSense の審査に落ちたりポリシー違反と判断されたりするリスクがある。一方で、PoC 期間の広告収益はほぼゼロと見込まれ、リスクに見合わない。広告がなければ、同意管理（CMP）の導入と、Week 8 の広告作業も不要になる。
  * 収益化は、アプリ化の判定（1.1）を通過した後に 5.2 の方針で検討する。
* 遊び方・結末と称号の解説・開発秘話などの**テキストページ**は、検索流入と SNS からの理解促進のために静的に用意する（Phase 2）。
* Web版においては短期的な収益最大化よりも「熱狂度と拡散力の検証（PoC）」を主目的とする。

### 5.2 スマホアプリ展開時の採算ラインとマネタイズ設計
* **アプリ維持コストの回収損益分岐点：**
  * 年間維持費（Apple Developer Program 約1.5万円/年 ＋ インフラ費用）の回収ライン：
    * リワード広告（想定eCPM 1,500円〜2,500円 / 1再生あたり約2円）：年間 **7,500回以上の広告再生（＝月間1,000〜2,000 DAU）** で黒字化。
* **App Store Review Guidelines 4.2（最低限の機能）への対策（v1.11）：** Web 版をラップしただけのアプリはリジェクトされやすい。アプリ化するときは、アプリ版だけの機能（触覚フィードバック、Game Center 連携、日替わりの通知など）を入れる方針とする。
* **アプリ化時のマネタイズ導線（先行予約）：**
  1. **動画リワード広告（Rewarded Video）：** **プレイ中の延命には使わず、プレイの外（リザルトの後）の特典に限定する**（v1.12）。
     * 候補：倒産後に「裏話・開発秘話カード」を1枚解放する、など図鑑の拡張。次のランの開始条件を少し有利にする特典（例：1項目だけ初期値 +10）は、バランスと記録の価値に影響するため、採用する場合はシミュレータで検証し、記録には「特典あり」と表示する。
     * 不採用：切り札の再装填、倒産時の巻き戻し（v1.11 まで記載）。理由は3つある。1プレイ30〜90秒のテンポを壊すこと、広告で生き返った記録はシェアしたくなる価値が下がること、巻き戻しには状態履歴の管理が必要になること。
  2. **買い切り課金（300円〜500円）：** バナー・インタースティシャル広告の完全非表示 ＋ 特殊経営スタイル（隠し会社タイプ）の即時解放。

4. **事業責任者・グロース用KPIイベントトラッキング（Cloudflare Web Analytics / GA4）：**

| イベント名 | パラメータ | 計測目的 |
| :--- | :--- | :--- |
| `game_start` | `style_id`, `is_retry` | ゲーム開始・選択スタイル |
| `play_duration` | `survival_week`, `duration_sec` | 1プレイ所要時間（タイパ検証） |
| `funnel_milestone` | `reached_week (13, 26, 39, 52)` | 四半期ごとの離脱ファネル分析 |
| `drop_at_week` | `week_number` | 途中離脱・ブラウザ破棄週の特定 |

* **`heartbeat_10s` の発火条件（v1.12）：** ラン開始（Week 1 のカード表示）から、ページが表示中（`visibilityState === 'visible'`）の時間の累計が10秒に達した時点で、**ユーザーにつき1回だけ**送る（送信済みかどうかは SaveData に記録する）。
* **KPI の算出式（v1.12。すべて GA4 内で完結させる）：**

  * 平均プレイ回数（1.1-3）＝ `game_start` のイベント数 ÷ `game_start` を送ったユーザー数
  * D1 / D7 リテンション（1.1-4）＝ `days_since_first_play` が 1 / 7 のイベントを送ったユーザー数 ÷ その日に初回プレイしたユーザー数（`days_since_first_play = 0` のユーザー数を日別に集計）

  * 注意：広告ブロッカーを使うユーザーは比率の計算から外れる。そのユーザー層だけ行動が異なる可能性は、判定時の留意点として記録する。

### 7.5 バランス検証（ヘッドレスシミュレータ）（v1.9 新設）
1. **目的：** 生存カーブ（3.1-6）、死因のバランス（3.1-2）、スタイル間の性能差（3.3）、称号の取得難度（3.5）を、手動のテストプレイに頼らず定量的に検証する。

3. **Bot の戦略：**
   * `random`：完全にランダムに選ぶ（初見プレイヤーの代わり）。
   * `greedy`：選択後に、4パラメータの「50からの最大の離れ」が最小になる方を選ぶ。切り札は、いずれかが危険域（≤15 または ≥85）に入ったときに使う（上級者の代わり）。
   * `gambler`：`cash` が増える方を優先する。
4. **合格基準（初期値。Phase 1 Week 4 で見直す）：**
   * `random`（初回プレイ相当。導入カードと序盤カードあり）の生存週数の中央値が Week 8〜15。
   * `greedy` のクリア率が 15〜35%。
   * 死因の発生比率（`random` と `greedy` の合算。v1.10）：下限死4種がそれぞれ **5%以上・25%以下**、上限死4種がそれぞれ **1%以上・15%以下**、上限死の合計が **10%以上・30%以下**。
   * スタイル別の `greedy` クリア率の差が10ポイント以内。
   * 各称号の `greedy` での取得率が、クリアしたランのうち1%以上（『スピード退職』『監査局の常連』は `random` の全ランで判定）。
5. **運用：** カード JSON を変更するたびに実行する。CI（GitHub Actions など）で、検証エラーや合格基準からの逸脱を警告として出す。

### 8.2 Router の動き（既存の仕組みに合わせる）
- `/genkai-ses` → `/genkai-ses/` へ 308 リダイレクト（Router が行う）。
- `/genkai-ses/*` → オリジンへ転送する。**転送時に先頭の `/genkai-ses` を削る**（例：`/genkai-ses/assets/app.js` → オリジンの `/assets/app.js`）。
- Router はオリジンのレスポンス（ステータス、ヘッダー、本文）を書き換えない。オリジンがエラーを返しても、別のオリジンに切り替えない。
- ステージングは `https://staging.promptlab-games.com/genkai-ses/`（同じ Worker が、本番と同じオリジンへ転送する）。

### 8.3 ゲーム側の技術制約
1. **公開パス：** Vite の `base` を `/genkai-ses/` にし、JS・CSS・画像・フォントの URL がすべて `/genkai-ses/` から始まるようにする。`<link rel="icon">` なども `%BASE_URL%` で書く。
2. **オリジン上のパス：** オリジンは先頭を削った後のパス（`/`、`/assets/…`、`/results/…`）で受け取る。`dist` の構成はこのパスに合わせる（`dist/genkai-ses/` のような入れ子にしない）。
3. **リダイレクトを起こさない：** Cloudflare Pages は末尾スラッシュをそろえるリダイレクトを相対パスで返し、Router 経由では公開パスが抜けてしまう。そこで、物理的なディレクトリに `index.html` を置かない（トップの `index.html` を除く）。結末ページは `results/{slug}.html` にし、アプリ内のリンクと canonical は末尾スラッシュなしで書く。
4. **SPA：** 直接アクセスとリロードは、Pages の既定の SPA フォールバックで受ける（`_redirects`・`404.html` は置かない）。未知のパスはアプリ内でタイトル画面に戻す。
5. **保存データ：** LocalStorage は、ブランドの全タイトルで同じオリジンを共有する。キーは必ず `genkai_ses_` で始め、他タイトルのキーを読み書きしない。
6. **プレビュー環境：** Pages のプレビュー（`*.pages.dev`）では公開パスが付かないので、`develop` 以外のブランチのビルドでは `base` を `/` にする（Pages の環境変数 `CF_PAGES_BRANCH` で切り替える）。
7. **計測タグ：** Cloudflare Web Analytics の JS スニペットと GA4 は、ゲームのページ（`index.html` と結末ページ）にだけ入れる。Portal と他タイトルには影響させない。

### 8.4 検証（CI と自動テストを優先する）
| 対象 | 検証 |
|---|---|
| ゲーム（このリポジトリ） | CI（lint、単体テスト、カード検証、シミュレータ、ビルド、E2E）。**公開パス付きの本番ビルドを、先頭を削るプロキシ越しに配信して E2E を行う**（既存タイトルの `base_path` テストと同じ考え方）。確認すること：起動、JS・CSS・画像・フォントの取得、直接アクセスとリロード、結末ページの OGP と遷移、リダイレクトが起きないこと |

- [ ] Cloudflare Pages のビルドとデプロイが成功している
- [ ] 共通ドメイン配下の公開 URL（`/genkai-ses/`）から正常に起動する
- [ ] JavaScript・CSS・画像・フォントが正常に取得できる（本作は効果音を Web Audio API で合成するので、音声ファイルはない）
- [ ] 直接アクセスとリロードに問題がない（トップ、結末ページ、未知のパス）
- [ ] Portal からゲームへアクセスできる
- [ ] 既存の KANBAN PANIC・OFFICE CLASH が正常に動作する
- [ ] 公開手順が README などに記録されている
- [ ] ブランドのプライバシーポリシーが、本作の計測を反映している

### 8.7 ブランドの AdSense 審査との関係
- ブランドは同じドメインで AdSense の審査を受けており、「有用性の低いコンテンツ」で承認されていない状態が続いている。本作は、Web 版 PoC では広告を置かない（5.1）。そのうえで次の2点で、ドメインの評価を下げず、むしろ上げる側に回る。
  1. 露骨な違法用語を使わない（3.6-8）。
  2. Phase 2 で、既存タイトルと同じ形のテキストページ（ゲームの設計、開発の過程などの解説記事）を同じドメインに載せる（6章 Week 8）。
